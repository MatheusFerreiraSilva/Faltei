# Security Specification — faltei.

## 1. Data Invariants
1. **Strict Tenant Isolation**: Documents under `/users/{userId}/materias/{materiaId}`, `/users/{userId}/faltas/{faltaId}`, `/users/{userId}/eventos/{eventoId}`, and `/users/{userId}/config/{configId}` (specifically `notificacoes` & `fcmToken`, with `allow list: if false` on `/config`) are readable and writable exclusively by the authenticated owner (`request.auth.uid == userId`), or read via `get` by a verified administrator for support.
2. **Relational Integrity (Master Gate)**: A `UserFalta` under `/users/{userId}/faltas/{faltaId}` cannot be created unless the parent `UserMateria` referenced by `materiaId` exists at `/users/{userId}/materias/{materiaId}` and `userId` matches `{userId}`. An optional `materiaId` on `UserEvento` must likewise resolve to an existing parent `UserMateria` on both `create` and `update`.
3. **Role & Email Binding Protection**: Regular users creating `/users/{userId}` are restricted to `role: "student"` unless verified as an administrator (`isAdmin()`), must bind `email` to `request.auth.token.email`, cannot provide an empty `displayName`, and cannot escalate their own `role` during updates.
4. **Catalog & Semester Governance**: `/config/{configId}` and `/catalogo_disciplinas/{disciplinaId}` require authenticated reads (`request.auth != null`); mutations (`create`, `update`, `delete`) require `isAdmin()` with verified email (`request.auth.token.email_verified == true`), and validate structured `feriados[0]`, `horarios[0]`, and `blocosAula[0]` shapes.
5. **Temporal, ID & Schema Integrity**: Every create and update enforces strict key allowlists (`hasAll`/`hasOnly` on create, `affectedKeys().hasOnly(...)` on update), path-safe `isValidId` (`1..128` chars, `^[a-zA-Z0-9._-]+$`, rejecting `.` and `..`), strict 24h `HH:MM` time validation (`^([01]\d|2[0-3]):[0-5]\d$`), bounded string/array sizes (`horarios <= 7`, `blocosAula <= 14`), valid enum values (`tipoFalta in ['dia_completo', 'turno_manha', 'turno_tarde', 'turno_noite', 'parcial']`), bounded hours (`0.5 <= horasAbatidas <= 24`), and server-verified timestamps (`request.time`) on `createdAt`/`updatedAt`.
6. **Collective Discipline Enrollment & Notice Integrity (Bloco 4)**: Enrollment in `/disciplinas_comunidade/{disciplinaKey}` uses atomic `existsAfter`/`!existsAfter` pairs against `/inscritos/{userId}` with strict `+1`/`-1` deltas and non-negative decrement floor (`existing().inscritosCount >= 1`), keeping `/inscritos` private (`owner`/`admin` only) and `avisos_coletivos` restricted to enrolled peers (`autorUid == request.auth.uid`, `isOficial` admin-only).
7. **Sem Aula Consensus Integrity**: `/sem_aula_consenso/{consensoId}` uses atomic `existsAfter`/`!existsAfter` pairs against `/votos/{userId}` with strict `+1`/`-1` deltas on `votosCount`, preserves `ultimoAutorNome` during vote withdrawal (`-1`), and keeps per-user votes private (`owner`/`admin` only).
8. **Collective Events & Vote Integrity (Radar da Turma)**: `/disciplinas_comunidade/{disciplinaKey}/eventos_coletivos/{eventKey}` enforces parent community existence and enrolled-peer/admin membership on `create` and voting `update`, `titulo.size() <= 120`, `contagem == votosUserIds.size()` (bounded `1..500`, string items), and `request.auth.uid in request.resource.data.votosUserIds` on creation and voting, preventing vote inflation while preserving author/admin edit control.

## 2. The "Dirty Dozen" Adversarial Payloads
1. **Cross-Tenant Read/Write**: User B attempts to read or write `/users/userA/materias/mat1` -> `PERMISSION_DENIED`.
2. **Shadow Field Injection on Materia or Notification Config**: User A creates a `UserMateria` or updates `/users/{uid}/config/notificacoes` with an extra ghost key `isApprovedByAdmin: true` -> `PERMISSION_DENIED`.
3. **Self-Role Escalation**: Student registers `/users/{uid}` with `role: "admin"` -> `PERMISSION_DENIED`.
4. **Role Escalation via Update**: Student updates `/users/{uid}` changing `role` from `"student"` to `"admin"` -> `PERMISSION_DENIED`.
5. **Email Spoofing Attack on Admin or User Profile**: Attacker sets email to admin email with `email_verified: false` to overwrite `/config/semestre_atual`, or registers `/users/{uid}` with someone else's email -> `PERMISSION_DENIED`.
6. **Orphaned Falta or Evento Creation/Update**: User A creates a `UserFalta` or updates a `UserEvento` referencing a non-existent `materiaId: "ghost_materia"` -> `PERMISSION_DENIED`.
7. **Owner UID Spoofing**: User A creates `/users/userA/faltas/f1` with `userId: "userB"` -> `PERMISSION_DENIED`.
8. **Resource Exhaustion / Dot-Segment ID**: Attacker attempts to create a document with `materiaId` of 1500 characters or `".."` -> `PERMISSION_DENIED`.
9. **Unbounded Array or Malformed Element Attack**: Attacker creates a `UserMateria` with 500 items in `horarios` or invalid `horarioInicio: "99:99"` -> `PERMISSION_DENIED`.
10. **Value Poisoning on Update**: User A updates `UserFalta.tipo` to `"hacked_type"`, `horas: 999`, or `horarioNoturno: "29:99"` -> `PERMISSION_DENIED`.
11. **Timestamp Forgery**: Attacker sends `createdAt` in the past/future instead of `request.time` -> `PERMISSION_DENIED`.
12. **Catalog Tampering, Un-enrolled Posting & Counter Inflation**: Authenticated student attempts to write `/catalogo_disciplinas/med1`, post to `/disciplinas_comunidade/{key}/eventos_coletivos` without enrollment, inflate `inscritosCount: 999`, overwrite `ultimoAutorNome` on `-1` vote, or forge `isOficial: true` on `avisos_coletivos` -> `PERMISSION_DENIED`.
